# Cryptographic Namespace & Data Architecture Strategy

## Overview

A data architecture where every interaction, object, or record is assigned a cryptographic identity. Ownership, provenance, addressing, and access control collapse into a single unified system — no central registry, no coordination between users, no trust required in the infrastructure.

---

## Core Principles

### 1. Identity-Derived Addressing

Each user or entity holds a **cryptographic keypair** (e.g. Ed25519). Their public key defines their **namespace** — an infinite, non-overlapping partition of the global address space. No coordination with other users is required because the math guarantees uniqueness by construction.

- No central counter or registry
- No race conditions on ID generation
- New identities are self-sovereign — generated offline, independently
- Namespaces never overlap across different keys

This is the same principle used by **Tor v3 .onion addresses**, where the address is a base32-encoded public key — the address *is* the identity.

---

### 2. Part Numbers / Record IDs as Cryptographic Signatures

A record identifier is generated by signing a serial number (or any unique value) with the user's **private key**. The resulting value serves simultaneously as:

| Function | Traditional System | This System |
|---|---|---|
| Generate identifier | Separate step | ← Same operation |
| Record authorship | Database entry | ← Same operation |
| Sign/approve record | Separate workflow | ← Same operation |
| Prove authenticity | Trust the database | ← Verify the math |

The signature **is** the part number. Provenance is intrinsic to the identifier — not metadata stored elsewhere.

No one can forge an identifier in your namespace without your private key. No central authority is needed to validate authenticity.

---

### 3. Branching is Free

Because each keypair defines its own namespace, **branching requires no coordination**:

- Every key is already a branch by definition
- Sub-identities or sub-keys create sub-namespaces naturally
- Merging is an explicit act — re-encrypting a record to a shared or team key
- The branch hierarchy is encoded in the key derivation path, not in a database

A whole list of records can exist publicly. Only records that **resolve against your key** (i.e. decrypt successfully) belong to your branch. Failed decryption means "not yours" — the address simply doesn't resolve.

---

### 4. Three-Layer Data Model

Every record consists of three distinct information layers:

```
┌─────────────────────────────────────┐
│  PUBLIC HANDLE                      │  ← Opaque reference, globally visible
│  Correlatable without decryption    │
├─────────────────────────────────────┤
│  PRIVATE METADATA                   │  ← Embedded in handle, key-holder only
│  Readable with private key          │
├─────────────────────────────────────┤
│  PAYLOAD                            │  ← LUKS (or equivalent) container
│  Decryptable by authorized parties  │
└─────────────────────────────────────┘
```

**Public handle** — An opaque but correlatable reference. Useful for indexing, graphing relationships, and routing without revealing content. No decryption required.

**Private metadata** — Embedded within the handle itself, readable only by the key holder. May include timestamps, type tags, relationship pointers, or other structured data. The handle is not just an address — it carries a private channel inside it.

**Payload** — A LUKS (Linux Unified Key Setup) or equivalent encrypted container holding the actual data. Decryptable only by parties holding an authorized key.

---

### 5. Separation of Correlation and Decryption

A fundamental property of this architecture: **you can correlate records without decrypting them**.

| Operation | Requires Decryption? |
|---|---|
| Does this record exist? | No |
| Is record A related to record B? | No |
| Who created this record? | No |
| When was it created? | No |
| What type of record is it? | No |
| What is the content? | Yes — private key |
| What is the payload data? | Yes — LUKS key |

This means a fully functional index, graph database, and correlation system can be built on top of completely encrypted data. The database operator never needs to see plaintext. The system can run on **untrusted infrastructure**.

---

### 6. Access Control via LUKS Keyslots

LUKS supports multiple **keyslots** — multiple authorized openers for the same container. This maps cleanly to access control without a separate permissions system:

- **Private draft** — encrypted to your key only
- **Team release** — add team key to keyslot
- **Customer delivery** — add customer key to keyslot
- **Revocation** — remove keyslot

The record's handle/identifier never changes. The container doesn't move. Access is extended or revoked by keyslot management alone. No ACL tables, no permissions database, no user management system.

---

## Supply Chain & Provenance Implications

Because the part number is a cryptographic signature:

- A vendor or customer can **independently verify origin** without contacting you
- No trusted intermediary is required to validate "is this a real part number"
- Counterfeit detection is a cryptographic operation, not a database lookup
- The full chain of custody can be encoded as a chain of signatures, each referencing the prior

## Relationship to Existing Systems

| System | Relationship |
|---|---|
| Tor v3 .onion | Same addressing principle — public key *is* the address |
| IPFS | Content addressing — hash of content is the address |
| BitTorrent v2 | File-level content hashing, Merkle tree structure |
| LUKS | Payload encryption layer with multi-keyslot access |
| PGP Web of Trust | Key-based identity, but centralized trust model |
| Tahoe-LAFS | Capability-based filesystem — read capability = address |
| Secure Scuttlebutt | Identity-based append-only log, feeds are key-derived |
| Zero Knowledge Proofs | Prove facts about data without revealing data |
| Homomorphic Encryption | Compute on encrypted data — complementary technique |

This architecture **generalizes** these systems into a unified data model applicable to any domain — parts databases, document management, supply chain, filesystems, or general data infrastructure.

---

## Key Properties Summary

- **No coordination required** between users or systems
- **No central registry** — the math guarantees uniqueness
- **Infinite address space** per identity
- **Provenance is intrinsic** — embedded in the identifier, not stored separately
- **Branching is structural** — encoded in key hierarchy, not database schema
- **Correlation without decryption** — public infrastructure, private data
- **Access control = cryptography** — no separate permissions system
- **Runs on untrusted infrastructure** — operator never sees plaintext
- **Offline generation** — no network required to issue new identifiers

---

## Open Design Questions

- **Key loss** — if a user loses their private key, their namespace is orphaned; backup and recovery strategy needed
- **Key rotation** — handling expiry or compromise without breaking existing references
- **Human readability** — cryptographic handles are not bench-friendly; a short alias layer may be needed for operational use
- **Lookup / resolution** — an index is needed to resolve handle → record location; this index can itself be encrypted
- **Revocation propagation** — how keyslot revocations are communicated to distributed nodes
